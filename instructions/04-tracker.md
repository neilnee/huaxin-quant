- **版本管理**: 由 Git 分支与提交历史管理，文件名不再携带版本号
- **最近更新**: 2026-07-05
- **核心目标**: 模型四负责把模型二、模型三和持仓数据整合成最终跟踪与交易管理体系。当前阶段已落地 Bloom 发现侧和持仓账本管理第一版，估值触发层与持仓策略监控后续独立补齐。
- **总控边界**: 模型四不是单一脚本逻辑，而是多个独立信号模块的统一调用层。

## 当前总控结构

模型四拆为三个相对独立的模块：

```text
模型四 Tracker 总控
├── Bloom 信号层
├── 估值触发层
└── 持仓管理层
```

| 模块 | 指令卡 | 当前状态 | 职责 |
|------|--------|----------|------|
| Bloom 信号层 | `instructions/signal-bloom.md` | 当前实现重点 | 消费模型二结果，判断候选信号质量、风险阻断、观察状态、估值候选 |
| 估值触发层 | 后续新增 `instructions/signal-valuation-queue.md` | 暂不实现 | 基于 Bloom 结果判断哪些股票值得进入模型三估值 |
| 持仓管理层 | `instructions/signal-position.md` | 账本层第一版实现 | 独立维护交易流水、当前批次和每日持仓状态，后续再接策略监控 |

所有模块指令卡统一放在 `instructions/` 目录下。`signal-` 前缀表示模型四内部的独立信号模块。

## 模块边界

Bloom 信号层只回答：

```text
这只模型二发现的股票，当前信号质量如何？
是否值得重点跟踪？
是否被量价风险阻断？
是否值得送估值？
下一步观察点是什么？
```

Bloom 不回答：

```text
当前是否正式买入？
应该买多少仓位？
持仓是否止盈止损？
估值是否有安全边际？
```

估值触发层后续独立实现，消费 Bloom 输出，判断哪些股票值得进入模型三估值流程。

持仓管理层先独立维护账本。后续策略监控再消费持仓状态、Bloom 信号和行情量化指标；模型三估值只作为人工参考，不作为自动买卖硬依据。

## 当前验收标准

- Bloom 状态、信号、池子决策全部使用大写枚举。
- Bloom 不重新判断 VCP 阶段，不覆盖模型二的 `structure_stage` / `setup_signal`。
- Bloom 能基于连续状态变化输出 `NEW_ENTRY`、`UPGRADE`、`DOWNGRADE`、`SETUP_TRIGGER`、`RISK_BLOCK`、`COOLDOWN`、`EXIT`、`DATA_HOLD`、`CONTINUED`。
- Bloom 输出可被后续估值触发层和持仓管理层直接消费。
- 当前阶段不接模型三估值，不接持仓，不写 `signals/positions.csv`。

- **输出**:
  - `signals/signals_<YYMMDD>.md`（每日个股信号详细报告）
  - `core_pool.csv`（更新后的核心跟踪池）

- **配套脚本**:
  - `scripts/tracker.py` — 数据拉取、缓存管理、技术指标计算、信号条件预检、**池子维护**，输出 `signals_<YYMMDD>.json`
  - `scripts/generate_report.py` — 读取 JSON + `valuation_ranking.csv`，自动生成 `signals_<YYMMDD>.md` 报告
  - LLM 职责：阶段零交互确认、阶段二信号解读与操作建议措辞、阶段四估值复核提醒（报告格式化由脚本完成，LLM 不做排版）
- **参考手册**: `04-tracker-ref.md`（信号常量、指标公式、函数规格，足以重建脚本；执行时不加载）

## 总览

每日收盘后运行，分六个阶段：

```
阶段零（池子维护）→ 阶段一（数据拉取）→ 阶段二（信号扫描）
→ 阶段三（前瞻预警）→ 阶段四（估值复核）→ 阶段五（交互确认与输出）
```

**核心设计原则**:
- **脚本算数值 + 出报告，LLM 做判断**：`tracker.py` 拉数据算指标 → `generate_report.py` 出报告 → LLM 负责信号解读、仓位分析、操作建议措辞
- 支撑止损看买入逻辑是否被破坏，均线止盈看趋势是否转折
- 量价关系贯穿所有信号：缩量放宽容忍度，放量收紧触发条件
- 仓位越重，止盈止损线越紧
- 前瞻预警不执行交易，只提醒明天盘中关注

## 阶段零：池子维护

### 目标
更新核心跟踪池，确认仓位状态。

### 关键文件结构

**core_pool.csv**（不存在时创建）：

```
code,name,first_added,last_quant_date,consecutive_miss,priority,has_valuation,status,entry_pattern,entry_ma
```

| 字段 | 说明 | 示例 |
|------|------|------|
| code | 股票代码 | `="300442"` |
| name | 股票名称 | 润泽科技 |
| first_added | 首次调入日期 | 2026-05-20 |
| last_quant_date | 最近一次出现在模型二精选池的日期 | 2026-05-19 |
| consecutive_miss | 连续未在最新 quant 中出现的次数 | 0 |
| priority | 优先级标记 | `优先` / `正常` |
| has_valuation | 估值报告是否已完成 | TRUE / FALSE |
| status | 跟踪状态 | `跟踪中` / `观察中` / `已移出` / `ETF跟踪` |
| entry_pattern | 模型二买入形态（首次入池时记录，后续不覆盖） | `A` / `B` / `C` / 空 |
| entry_ma | A类形态的支撑均线（首次入池时记录） | `MA20` / `MA60` / 空 |

**entry_pattern 维护规则**：
- 标的首次调入 core_pool 时，从 quant CSV 的"通过类别"列读取，写入 `entry_pattern`
- 对于 A 类，同步从 quant CSV 的 `entry_ma` 列读取支撑均线
- 已存在于 core_pool 的标的，即使后续重新入选 quant 且类别不同，也**不覆盖** `entry_pattern`——卖出逻辑应始终对应买入时的逻辑
- 空值（手动加入、ETF、历史遗留）→ 使用默认信号参数（不区分形态）

**ETF 跟踪说明**：ETF 不经过模型一/二/三（无财报、无量价形态分类、无估值模型），因此：
- `has_valuation` 填 `N/A`
- `status` 填 `ETF跟踪`
- 信号扫描仅适用：S0-硬止损、S4-均线破位、S2-移动止盈（部分适用，ETF 无量价逻辑中的"主力行为"概念，仅看趋势）
- 其余信号（B1/B2/S1/S3/S5/W3）全部跳过
- 前瞻预警：仅适用 W1（价格预警）和 W2（量价预警）
- 估值复核全部跳过

**positions.csv**（不存在时创建空模板）：

```
code,name,asset_type,target_type,target_value,actual_shares,cost_price,stop_loss_override
```

| 字段 | 说明 | 示例 |
|------|------|------|
| code | 股票代码 | `="300442"` |
| name | 股票名称 | 润泽科技 |
| asset_type | 资产类型 | `个股` / `ETF` |
| target_type | 目标计量方式 | `shares`（按股数）/ `amount`（按金额元） |
| target_value | 目标值 | shares→股数（如 1000）；amount→金额元（如 60000） |
| actual_shares | 实际持仓股数 | 500 |
| cost_price | 持仓成本价（元） | 3.048 |
| stop_loss_override | 个人止损比例覆盖（空=用默认值） | -0.15 |

仓位状态判定规则：
- **目标类型为 shares**（个股，按股数管理）：
  - 未持仓：actual_shares = 0
  - 轻仓：actual_shares ≤ target_value × 50%（5 成及以下）
  - 标准仓：actual_shares 超过 target_value 的 50%，不足 75%
  - 重仓：actual_shares ≥ target_value × 75%
- **目标类型为 amount**（ETF，按金额管理）：
  - 未持仓：actual_shares = 0
  - 轻仓：actual_shares × 最新价 ≤ target_value × 50%（5 成及以下）
  - 标准仓：actual_shares × 最新价 超过 target_value 的 50%，不足 75%
  - 重仓：actual_shares × 最新价 ≥ target_value × 75%

> **仓位状态计算**：总持仓 = positions.actual_shares + 所有活跃批次的 shares 之和。仓位分层基于总持仓 / 目标值，不区分底仓和批次。

**batches.csv**（加仓批次监控，不存在时创建空模板）：

```
batch_id,code,name,entry_date,entry_logic,entry_ma,shares,cost_price,stop_loss_override
```

| 字段 | 说明 | 示例 |
|------|------|------|
| batch_id | 批次唯一标识 `{code}-{seq}` | `300442-1` |
| code | 股票代码 | `="300442"` |
| name | 股票名称 | 润泽科技 |
| entry_date | 买入日期 | 2026-05-21 |
| entry_logic | 触发逻辑 | `B1` / `B2` / `手动` |
| entry_ma | B1 的支撑均线，其余留空 | `MA60` |
| shares | 该批次股数 | 100 |
| cost_price | 该批次成本价（元） | 98.50 |
| stop_loss_override | 个人止损比例覆盖（空=用默认） | -0.08 |

**分仓规则**：positions.csv=底仓不动，batches.csv=浮动加仓。批次卖出信号独立检查，B1/B2仍为股票级别判断。ETF不参与分仓。

**trade_log.csv**（交易记录，不存在时创建空模板）：

```
trade_id,code,name,entry_date,entry_logic,shares,entry_price,exit_date,exit_price,exit_reason,pnl_pct
```

批次买入→卖出闭环后，从 batches.csv 删除，在此记一笔供复盘。只增不删，不参与信号计算。

## 阶段一：数据拉取

### 目标
由 `tracker.py` 拉取核心池所有标的的近60个交易日日线数据，计算技术指标，输出结构化的指标快照供 LLM 在阶段二中引用。

### 执行方式

```bash
python3 scripts/tracker.py                           # 默认：读取 core_pool.csv，拉取全部标的
python3 scripts/tracker.py --test                    # 测试模式：只跑前 3 只
python3 scripts/tracker.py --code 300442             # 单只更新
python3 scripts/tracker.py --no-cache                # 强制跳过缓存，重新拉取
```

### 脚本职责

**1.1 日线数据拉取**
- 从 `core_pool.csv` 读取标的列表，拉取近 60 个交易日日线
- 缓存至 `cache/daily/<code>_<YYMMDD>.pkl`，与模型二共享
- 数据链路与模型二共享：运行日缓存 → 最近可用缓存（需最新 K 线不早于目标交易日）→ 妙想 API → 通达信 mootdx 备用源
- 日线缓存按文件修改时间保留 30 天，脚本启动时自动清理超过 30 天未修改的 `cache/daily/*.pkl`
- 当妙想限流、返回空数据、结构异常、异常抛出，或本地未配置 `MX_APIKEY` 时，脚本必须尝试通达信备用源。通达信通过 mootdx 获取日线 `frequency=9`，客户端使用内置 HQ 候选服务器、短超时和失败切换，避免批量运行长时间阻塞。通达信不提供换手率，`turnover` 填 `0.0`；模型四信号不得依赖 `turnover`

**1.2 技术指标计算**

| 指标 | 用途 |
|------|------|
| MA5 / MA10 / MA20 | 均线止盈 / 破位判断 |
| MA20 斜率（%/天） | S4 均线走平判断 |
| 量比（当日成交量 ÷ 前 5 日均量） | 放量 / 缩量判别 |
| 缩量程度（近 5 日均量 ÷ 近 20 日均量） | 缩量回调 / 量价背离 |
| 近 5 日涨幅 | 加速赶顶判断 |
| 近 20 日最高价 / 最低价 | 箱体上下沿 / 支撑参考 |

**1.3 箱体形态检测（B2 输入）**
- 箱体盘整：近 20 日价格区间 ÷ 均价 < 15%
- 突破信号：今日收盘 ≥ 近 20 日最高价 × 98%
- 输出布尔标记：`box_consolidation`、`box_breakout`

**1.4 估值锚点加载**

`tracker.py` 和 `generate_report.py` 均从 `reports/indexes/valuation_ranking.csv` 读取以下字段：

| valuation_ranking.csv 字段 | 模型四用途 |
|-------------------|-----------|
| 下行风险价_元 | S0 支撑位底线 |
| 悲观估值_元 | B1/B2 价格区间下沿（⚠️ 字段名是"悲观"不是"保守"） |
| 基准估值_元 | B1 价格区间上沿 |
| 乐观估值_元 | B2 价格区间上沿、S1 估值卖点基准 |
| 安全边际折扣率 | 跨标的优先级参考 |

无估值报告的标的，估值字段为空，B1/B2/S1 信号自动跳过。

> **交叉验证**：`tracker.py` 和 `generate_report.py` 使用相同的字段名（`悲观估值_元`）和相同的 B1 价格条件（`悲观估值 ≤ 现价 ≤ 基准估值`）。generate_report.py 独立重算 B0/B1/T0 作为交叉校验层——两套计算结果应一致，不一致时报告以 generate_report.py 为准，同时说明 tracker.py 可能存在 bug。

**1.5 信号条件预检**

脚本对每只标的逐条检查买入/卖出信号条件，输出各信号命中情况及关键数值。LLM 不做数值计算，只做解读和操作建议。

### 预期输出

每只标的输出结构化指标摘要，包含：技术指标最新值、估值锚点、各信号条件命中情况、箱体检测结果。

## 阶段二：信号扫描

### 目标
基于 `tracker.py` 输出的指标快照和信号预检结果，逐只解读买入/卖出信号，结合量价关系和仓位状态输出操作建议。

**重要**：非持仓标的仅展示买入信号（B1/B2），不展示卖出信号。

### 2.1 买入信号

信号条件阈值的权威定义见参考手册 §信号条件常量速查。以下描述各信号的意图和特殊逻辑。

**B1 — 估值区间缩量回调**：现价落在悲观~基准区间 + 缩量 + 近MA。三个条件全满足触发，无估值则跳过。

B1 触发后按折扣率分四档建议（分档阈值见参考手册 §B1 建议分档），仓位建议（见参考手册 §仓位分档参数）。

**B2 — 箱体放量突破**：现价落在悲观~乐观区间 + 箱体盘整突破 + 放量。三个条件全满足触发，无估值跳过。标准仓时量比>2.0可加一次仓。

**B0 — 形态到位（B1/B2 前提条件不满足）**

由 `generate_report.py` 独立计算。触发条件：缩量程度 < 0.8 + 近MA（距MA20或MA60在-5%~+3%），但B1/B2价格条件不满足。B0 按估值位置分三类：

| 估值位置 | 报告标签 | 含义 | 建议 |
|----------|---------|------|------|
| 远超乐观（现价 > 乐观估值） | ✗贵 | 形态到位但太贵 | 等回调，不追买 |
| 深度低估（现价 < 悲观估值） | ⚡低价 | 形态到位但便宜到可疑 | 复核估值假设 |
| 缺估值报告 | 形态到位 | 无量价锚点 | 优先生成估值报告 |

B0 不是交易信号，是"值得关注但先别动"的提示。

**T0 — 买入逻辑有效性检查**（B1 触发时 `generate_report.py` 自动执行）

从 `core_pool.csv` 读 `entry_pattern`/`entry_ma`，检查买入形态支撑是否仍有效。检查条件（见参考手册 §S0 支撑位定义）。支撑被破坏时 B1 降级带 ⚠️，建议列显示"⚠️等企稳"。T0 不阻止买入，只提醒技术面和估值面存在冲突。

### 2.2 卖出信号

**优先级总览**：

| 优先级 | 信号 | 核心逻辑 |
|--------|------|----------|
| 最高 | S0-支撑止损 | 买入逻辑被破坏 |
| 最高 | S0-硬止损 | 成本线失守，兜底 |
| 最高 | S1-估值卖点 | 价格透支，减半仓 + 触发估值复核 |
| 高 | S5-加速赶顶 | 情绪极端 |
| 中 | S4-均线破位 | 趋势转折（覆盖 S2） |
| 低 | S3-量价背离 | 动能衰竭，早期预警 |

**S2 与 S4 的关系**：S4 覆盖 S2。当均线走平或向下时，只报 S4，不报 S2。S2 仅在均线仍保持上升（MA20 斜率 > 0.1%/天）但股价短暂跌破时触发。

---

**S0-支撑止损**：收盘价 < 支撑位 × (1 - 容忍度)。支撑位按买入形态差异化（见参考手册 §S0 支撑位定义），估值兜底不低于悲观估值×0.8。容忍度和操作建议见参考手册 §仓位分档参数。

**S0-硬止损**：当前价 < 成本价 × (1 + 止损比例)。止损比例见参考手册 §仓位分档参数。`stop_loss_override` 优先。不看量价，无条件执行。

**S1-估值卖点**：现价 > 乐观估值 × 1.1。任何持仓建议减仓至半仓以下，同时触发估值复核（见阶段四）。无估值则跳过。

**S4-均线破位**（覆盖 S2）：收盘价 < 止盈均线，且均线走平或向下。均线方向由 tracker.py 计算（走平|斜率|<0.3%/天，向下<-0.2%/天）。仓位差异化见参考手册 §仓位分档参数。

**S2-移动止盈**（仅均线上升时触发）：收盘价 < 止盈均线 + MA20上升 + 现价 > 成本×1.05。止盈均线按买入形态差异化（见参考手册 §仓位分档参数）。

**S3-量价背离**：近5日涨幅超阈值 + 缩量程度<0.6。涨幅阈值按形态差异化（见参考手册 §仓位分档参数）。

**S5-加速赶顶**：近5日涨幅>20% + 量比>2.5。任何持仓建议减仓或清仓，未持仓不追买。

---

### 2.3 信号叠加处理


当多信号同时触发时：

1. **卖出信号取最高优先级**：S0 > S1 > S5 > S4 > S3。报告只输出优先级最高的卖出信号，次高信号在"其他关注"中简要提及。例如 S1 和 S4 同时触发 → 报 S1（估值卖点优先于均线破位），S4 在脚注提一句"同时跌破 MA，关注趋势变化"。

2. **买卖信号同时触发**：同时报出。典型场景：
   - B1（估值到位）+ S3（量价背离但未恶化）→ 价格到了但还没企稳，你的判断决定是否现在建仓
   - B2（箱体突破）+ S5 临界（近 5 日涨 18%、量比 2.8，接近 S5）→ 突破有效但短期涨幅已大，需你判断追不追

3. **S2/S4 关系**：S4 覆盖 S2。当均线走平或向下时只报 S4。S2 仅在均线仍保持上升趋势时触发。

4. **S0 支撑止损 + S0 硬止损同时触发**：两个都报。操作建议取更紧急的（通常硬止损的减仓幅度更大）。

### 2.4 批次卖出信号（每批次独立检查）

当标的在 `batches.csv` 中有活跃批次时，对每个批次独立检查以下信号。批次信号与底仓信号互不影响。

**批次 S0-支撑止损**

支撑位按批次的 `entry_logic` / `entry_ma` 确定：

| entry_logic | 支撑位 | 说明 |
|-------------|--------|------|
| B1 | `entry_ma` 对应的均线（MA20 或 MA60） | B1 买的就是这条均线不破 |
| B2 | 箱体下沿（待激活） | 暂用近20日最低价兜底 |
| 手动 | 近20日最低价 | 通用默认 |

容忍度与底仓 S0 相同（轻仓5%/标准仓3%/重仓2%）。如有估值兜底，支撑位不低于悲观估值×0.8。

**批次 S0-硬止损**

用批次的 `cost_price`（而非底仓成本），可被 `stop_loss_override` 覆盖。止损比例与底仓相同（轻仓-12%/标准仓-10%/重仓-8%）。

**批次 S2-移动止盈**

仅当 `close > batch.cost_price × 1.05` 且均线上升时触发。止盈均线与底仓 S2 相同。

**不重复检查的信号**：S3（量价背离）、S4（均线破位）、S5（加速赶顶）是股票级别的量价信号，在批次维度不重复。底仓的报告已覆盖这些。

## 阶段三：前瞻预警

### 目标
扫描接近触发但尚未触发的信号，生成"明日关注"清单。

**W1-价格预警**

| 触发条件 | 提醒内容 |
|----------|----------|
| 当前股价距 S0 支撑止损位 < 2% | 明日若继续下跌将触发支撑止损 |
| 当前股价距 S4/S2 止盈均线 < 2% | 明日若跌破均线将触发卖出信号 |
| 近 5 日涨幅 > 15% + 量比 > 2.0 | 若明日早盘继续放量急拉，可能触发 S5 加速赶顶 |

**W2-量价预警**

| 触发条件 | 提醒内容 |
|----------|----------|
| 缩量程度 < 0.5 | 极度缩量，变盘前兆 |
| 近 3 日量比均 < 0.6 | 量能持续萎缩，关注方向选择 |

**W3-催化预警**

| 触发条件 | 提醒内容 |
|----------|----------|
| 模型三催化剂日历中的近期事件，预计触发时间在未来 2 天内 | 明日可能有催化落地，关注开盘反应（需该标的已有估值报告） |

## 阶段四：估值复核

### 目标
检测估值模型是否可能失真，在信号扫描之外独立提醒。

**异常检测条件**：

| 异常类型 | 判断条件 | 提醒内容 |
|----------|----------|----------|
| 价格严重偏离 | 当前股价 < 悲观估值×0.7，或 > 乐观估值×1.3 | 估值可能失真，建议人工复核 |
| 报告过期 | `valuation_index.csv` 中"数据截至报告期"距今超过 6 个月 | 估值可能过时，建议重新生成 |
| 一致预期修正 | 最新一致预期与估值报告中偏差 > 30%（当前需手动比对） | 市场预期已重大变化，建议重新估值 |

**S1 触发时的专项复核**：当 S1-估值卖点触发时，附加详细提醒：

```
⚠️ 估值复核提醒：
- 标的：<名称>(<代码>)
- 当前股价：XX.XX 元，已超出乐观估值(XX.XX 元) × 1.1
- 可能原因：模型未充分定价的预期差正在兑现 / 市场情绪驱动 / 估值假设需要调整
- 建议：重新审视模型三估值报告，确认是否需要上调估值中枢
- 是否现在触发模型三重新估值？（确认后执行）
```

## 阶段五：交互确认与输出

### 5.1 终末摘要

信号扫描完成后，终端打印分类摘要：

```
🔴 交易警报 — 底仓（明天执行）：
- <股票名称>(<股票代码>)：<信号类型>触发，<仓位状态>，<触发简述>，建议<操作>

🟠 交易警报 — 浮动批次（明天执行）：
- <股票名称>(<股票代码>) [批次ID]：<信号类型>触发，成本<XX>，浮盈<XX>%，建议卖出<XX>股

🟡 前瞻预警（明天关注）：
- <股票名称>(<股票代码>)：<预警类型>，<提醒内容>

⚠️ 估值复核提醒：
- <股票名称>(<股票代码>)：<异常类型>，<提醒内容>

📋 缺少估值报告的标的（建议在本次执行后逐一处理）：
- <股票名称>(<股票代码>)：缺少估值报告，B1/B2/S1 信号暂不可用
```

### 5.2 生成信号报告（脚本）

```bash
python3 scripts/generate_report.py <YYMMDD>
```

脚本自动完成：
- 读取 `signals_<YYMMDD>.json` + `valuation_ranking.csv` + `positions.csv` + `batches.csv`
- 生成总览表（持仓/未持仓分表，按 B1→B0→无信号排序）
- 生成 B1 聚焦表（排名、缩量、均线、T0、建议）
- 生成 B0 清单（有估值/缺估值分类）
- 渲染卖出信号详情 + 批次止损线
- 渲染手动标记抑制信号列表

**LLM 补充**：脚本生成的报告中，B1 建议列和卖出信号建议是通用的（"建议建仓""等企稳"等）。LLM 在报告生成后，针对触发了卖出信号的持仓标的和 B1 买点标的，在终端给出个性化解读和操作建议措辞（含具体比例和方向），不修改脚本生成的 markdown 文件。

### 5.3 解读重点

脚本覆盖了格式化和数据呈现，LLM 聚焦以下判断：
- 卖出信号：结合持仓成本、浮盈浮亏、仓位状态，给出个性化的减仓/清仓建议
- B1 买点：T0 冲突时判断等企稳还是现价建仓，安全边际大的优先
- 手动标记标的：虽抑制了卖出信号，但需提醒极端情况（如创新药浮亏-18%已超止损线）
- 终末摘要：按 🔴🟠🟡⚠️📋 分类口头播报

### 5.4 文件更新
- 更新 `core_pool.csv`（consecutive_miss、last_quant_date、status 等）
- 更新 `positions.csv`（如你在确认环节有变动）
- **批次闭环**：如你在确认环节确认执行批次卖出：
  1. 从 `batches.csv` 删除该批次行
  2. 追加一条记录到 `trade_log.csv`（含买入/卖出日期、价格、盈亏%）
  3. 更新 `positions.csv` 的 `actual_shares`（减去已卖出股数）
- **新增批次**：如你确认 B1/B2 买入信号并执行建仓/加仓，在 `batches.csv` 新增一行，batch_id 自增

## 上下游接口约定

**上游（模型二）**：读取 `quant/` 下最新日期的 CSV，文件名日期距今 > 5 天时打印提醒。模型四只消费模型二的新契约字段：

```text
structure_type / structure_stage / setup_signal / action_hint
structure_score / structure_risk_score / structure_risk_flags
support_price / invalid_price / breakout_level
```

模型二只描述量价结构事实和量价侧提示；是否进入跟踪池、是否需要估值、是否可买、仓位多少、持仓是否加减仓，均由模型四结合模型三估值、positions、batches 和人工标记决定。

**上游（模型三）**：读取 `reports/indexes/valuation_ranking.csv` 获取估值锚点。

**下游**：输出 `signals/` 目录下的每日信号报告，供次日盘前审阅。不自动触发任何上游模型。
